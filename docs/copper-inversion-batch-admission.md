# 跨分支整批准入

## 执行顺序

四分支模式通过共享 `HarnessClient.run_turn(submission_batch_validator=...)` 接收提交。每次收到新的封存快照，批量回调看到所有尚未答复的请求；返回值只包含本次要答复的 profile。未返回的请求保持等待，客户端继续处理其他分支的提交和 provider 授权。沿用原生协议，不增加第二套研究循环或提交状态库。

铜矿适配器按以下顺序处理：

1. 对当前待答复的全部源码检查严格数组结构、路径、摘要、语法、已测父身份、已测源码重复及跨分支重复。
2. 有静态错误时只要求错误分支修复，不运行任何接口 job。其他快照继续等待。
3. 本轮四个 profile 都有合法快照或持久准入回执后，才依次执行所有尚待答复候选的只读接口检查。
4. 每个通过项原子写入准入回执。接口错误仍通过原提交 validator 返回，可以在同一 turn 内修复；已通过项复用原执行回执。
5. 全部分支完成后才发布 reservoir；共享 engine 随后四选一并独立评分。

单 agent 保持共享单项 validator 路径，使用同一个数组提交契约和相同接口检查。

## 恢复与验证边界

共享客户端继续验证 turn 身份、最大提交次数、提交摘要与 native commit 一致性。每次重连重新收集未完成的原生提交；铜矿持久准入回执用于识别已经接受的同批源码。候选不能在恢复时更换已接受源码，也不能发布部分 reservoir。

定向测试覆盖：

- 静态检查发现重复或语法错误时，接口调用数严格为零。
- 四份源码已静态通过、第三次接口检查前中断：保留前两份准入回执，无 panel；恢复保持 fork plan 和源码，不增加正式评估数。
- 共享响应路由可以暂存先到的提交，接收后续提交或修复；存在未答复提交时拒绝整轮 commit。
- 真正 Python HarnessClient 与进程 fixture 通过批量回调完成原生格式的提交校验与计数。

这些测试区分任务 mock、共享协议 fixture 和真实模型运行。此前 P5 真实运行使用旧的逐分支准入顺序；不能将它当作新批量屏障的真实模型证据。最终模型端到端验收仍需使用冻结的新实现另建运行目录。

远程回归结果为 225 项通过；追加“中断时恰有两份准入回执”断言后，10 项定向测试再次通过。[机器证据及源码摘要](../tasks/copper_inversion/resources/evidence/runtime/batch-admission.json)记录了精确验证范围。
